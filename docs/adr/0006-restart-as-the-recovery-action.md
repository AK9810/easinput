# 恢复手段是真重启，不是进程内重置

**Status**: accepted (2026-11-24)

现场反馈：机器卡顿时切换输入法，easinput 没有跟上；此后气泡显示的模式与实际键入**持续不符**，退出并重新打开程序才恢复。

输入模式本身不会永久错——每次都是现读，卡顿造成的只是读取超时（漏一次，下一次轮询读回来）。会永久错的只有「启动时播种、之后靠事件维护」的状态：CapsLock 锁定态只在启动时从 `GetKeyState` 播种，之后仅由低级键盘钩子的按下事件翻转，没有任何对账；两个低级钩子在回调超时时会被系统静默摘掉，代码侧句柄仍然非零，没有存活检测。

**决定**：托盘菜单的「重启」是真重启进程——结束当前进程并立即启动一个新的。

**否决的方案**：进程内重新播种（重读 CapsLock、清空触发记忆、重装钩子）。它更快且没有空窗，但它是一张需要人工维护的清单：`BubbleController` 以后新增任何内存状态，忘了加进重置清单就会「点了没反应」，用户从此回到手工退出重开——等于这个功能没做。真重启按构造完整，不随代码增长而腐烂。

**Consequences**:
- 空窗约 0.4 秒（实测 441ms），期间没有气泡。
- 单实例互斥体先交给新进程再启动：旧进程先释放 Mutex，子进程带 `--restarted` 参数、拿不到时最多重试 3 秒。拉起失败时**保持运行**并弹托盘气泡报错，不出现「点了重启应用就没了」。
- 重启瞬间是这类漂移唯一可观测的时刻，所以把内存状态快照（跟踪的 CapsLock 值 vs `GetKeyState` 真值、`TriggerPolicy` 记住的模式与窗口）和钩子卸载返回值写进 **Warn 级**日志：默认 `logLevel: warn` 也能留下证据，用于日后定位到底是哪一种漂移。
- 顺带解决「手改配置后要重开」：新进程重新读配置。
